# iot-mqtt-ota-lab · MQTT 与 OTA 逻辑层（主机端可测）

面向 **ESP32 / 物联网固件**的两个核心协议模块，用**可移植 C99** 写成、**在主机上编译并跑自检测试**：

1. **MQTT 3.1.1 报文编解码**：变长"剩余长度"、PUBLISH（QoS0/1）、CONNACK / PUBACK / PINGREQ，QoS1 发送窗口（包 ID 分配、在途管理、窗口背压）。
2. **OTA 升级逻辑**：镜像头校验 → 顺序写入（拒绝乱序/越界）→ 全镜像 CRC32 → 启动标志 → **确认生效或回滚**，A/B 双槽。
3. **深睡策略**：Activity / Light-sleep / Deep-sleep 分级，待发数据与联网状态门控，唤醒周期。

> **为什么是"主机端"**：本机没有 ESP-IDF 工具链，**没有在 ESP32-S3 实机上验证过**（如实说明）。所以这里只做**与硬件无关的协议与逻辑层**——它们恰恰是最容易写错、也最值得单测的部分；板级部分（Wi-Fi/BLE 连接、esp_timer、NVS）需要实机才能验证，未包含在本仓库。

## 1. 构建与运行

```bash
make test     # 编译并运行自检测试（输出 PASS/FAIL 与汇总）
make clean
```

Windows 下产物为 `build/iot_tests.exe`；Linux 下把 `EXE` 置空即可。

## 3. 测试覆盖

| 组 | 覆盖内容 |
|---|---|
| MQTT 剩余长度 | 0 / 127 / 128 / 16383 / 16384 / 2097151 / 2097152 / 268435455 的**编码字节数与解码往返**；超 4 字节上限与非法 5 字节序列→失败 |
| PUBLISH 编解码 | QoS0 与 QoS1 往返；主题 / payload（含 `0x00`、`0xFF` 边界字节）一致；QoS1 包 ID 校验；QoS2 与空主题 → 拒绝 |
| 报文完整性 | 长度少一字节 / 剩余长度与实到字节不符 → **判定残缺并丢弃整包**（不交给上层） |
| 定长报文 | CONNACK `20 02 00 00`、PUBACK `40 02 12 34`、PINGREQ `C0 00` 逐字节校验 |
| QoS1 窗口 | 包 ID 从 1 开始、**到 65535 回绕跳过 0**；窗口满 → 背压；PUBACK 释放；重复/未知 PUBACK → 报错 |
| OTA 正常升级 | 头校验 → 分片写入 → **全镜像 CRC32 通过 → 确认后版本号生效**，新槽内容与镜像逐字节一致 |
| OTA 异常路径 | 坏 CRC → `OTA_ERR_CRC` + FAILED；**跳过一片或重复写 → 拒绝**；越过镜像长度 → 拒绝；magic 错 / 镜像大于分区 → 拒绝 |
| 续传与回滚 | 写入 100 字节后模拟断电 → 进度保留 → 从 100 续传后校验通过；自检失败 → **回滚且业务仍运行旧版本** |
| 深睡策略 | 500 ms 保持 ACTIVE / 1.1 s Light / 10 s Deep；**有待发数据或断网时禁止休眠**；唤醒周期 0 / 200 / 5000 ms |

## 4. 设计决策（面试常问）

1. **为什么"剩余长度"要单独写编解码？** MQTT 用 7 位一组的变长整数，最多 4 字节；**长度字段解析错误会导致整条报文错位**，而它又是所有报文共用的入口，所以单独测边界值（127/128、16383/16384）。
2. **收到长度不符的报文怎么办？** 直接判定残缺并丢弃整包，**不交给上层**——否则一个字节的偏差就会让上层把半条命令当完整命令执行。
3. **QoS1 为什么要发送窗口而不是"发出去就算完"？** QoS1 是"至少一次"，必须保留在途报文明细直到收到 PUBACK；窗口满要背压，否则断网时会无限堆积内存。包 ID **回绕必须跳过 0**（0 非法）。
4. **OTA 为什么用 A/B 双槽 + 启动标志？** 单槽升级失败就变砖；双槽可以在新镜像自检失败时**回滚到旧镜像**，状态机里 `pending → confirm / rollback` 就是这个流程。
5. **为什么只接受顺序写入？** 分片乱序意味着中间有丢失或重复，直接拒绝比"补齐"更安全；同时记录接收进度，**断电后可以从断点续传**而不是整包重来。
6. **深睡为什么要看联网状态？** 断网时睡下去就再也连不回来；有数据待上报时必须保持唤醒，所以睡眠决策要由业务状态门控，而不是单纯看空闲时间。

## 5. 局限（如实说明）

- **未在 ESP32-S3 实机验证**：只覆盖与硬件无关的协议与逻辑层；Wi-Fi/BLE 连接、esp_timer、NVS、真实 OTA 分区表未包含。
- MQTT 只实现 QoS0/QoS1（**QoS2 未实现**），未做 SUBSCRIBE/UNSUBSCRIBE 的完整编解码与遗嘱消息。
- OTA 未做**签名验签**（只有 CRC32 完整性校验），未做镜像加密与安全启动链。
- 未做压力测试与内存占用分析。
